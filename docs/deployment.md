# Размещение ClipForge

Принятая схема: один монорепозиторий; один контейнер приложения на ishosting
(Next production, API, планировщик); PostgreSQL в существующей инфраструктуре
Coolify; обработка медиа постоянным воркером на ПК; готовые клипы в Beget S3.
Сборка контейнера, проверки, публикация в GHCR и вызов деплоя Coolify выполняются
на GitHub-hosted `ubuntu-latest`. На ПК нет GitHub Actions runner.

## Роли процессов

- `WORKER_ROLE=control`: планировщик, обнаружение и индексация через Twitch API,
  статистика и публикация готовых видео из S3. Не запускает Python.
- `WORKER_ROLE=media`: только скачивание исходников, анализ/монтаж и запись в S3;
  очищает локальный кэш исходников. Не публикует на YouTube и не индексирует каналы.
  Нужны Python/CUDA, ffmpeg, постоянный доступ к общей БД и S3.
- `WORKER_ROLE=all`: прежний локальный режим разработки. Захватывает обе блокировки
  и не должен работать одновременно с распределённой установкой.

При выключении ПК сервер остаётся работоспособным, очередь сохраняется в БД,
автоматическое планирование новых тяжёлых задач ждёт свежего heartbeat от ПК.
Heartbeat сообщает свободное место именно на ПК, а не на сервере.
Публичные порты PostgreSQL для этого открывать не нужно: использовать SSH/VPN.

На текущем ПК задача Windows `ClipForge Media Worker` запускает supervisor из
`C:\Users\User\ClipForgeWorker`. Он поднимает SSH-туннель на 127.0.0.1:55433,
определяет текущий внутренний IP PostgreSQL и восстанавливает соединение при
обрыве. Задача запускается при входе пользователя в Windows; до входа в систему
и при выключенном ПК обработка недоступна. Docker Desktop и локальные CI-сборки
для этого не нужны. Прежняя задача `ClipForge GitHub Runner` удалена.

Настройки и секреты обработчика находятся в `.env` вне папок релизов.
Готовый media-runtime собирается и упаковывается на GitHub. После успешного
деплоя CI помещает его в закрытый GitHub Release. ПК проверяет серверную версию,
скачивает соответствующий архив через существующий вход GitHub CLI, сверяет
SHA-256 и переключает `current.json`. `pnpm`, TypeScript и Docker при этом
на ПК не запускаются. При неудаче остаётся предыдущая версия.
Supervisor перезапускает обработчик через IPC с завершением
очереди; прерванные задания восстанавливаются по правилам повторов pg-boss.
`DEPLOYMENT_MODE=distributed` отключает второй локальный планировщик при
`pnpm start`: локальный интерфейс использует общую серверную БД.

## Сборка и запуск

`.github/workflows/app.yml`: задание `build` на `ubuntu-latest` собирает сервер
без CUDA, Python, ffmpeg и моделей, проверяет его и отправляет образ в GHCR.
Задание `deploy` на другом GitHub-hosted runner вызывает webhook Coolify.
Работа обоих заданий не зависит от включённого ПК владельца.

CI сначала запускает `node scripts/test-container.mjs clipforge:ci` с временной
БД и томом. Только успешный образ получает теги SHA коммита и `latest` в GHCR.
Деплой считается успешным после ответа `/api/health/ready` с тем же SHA,
а не просто после принятия webhook или ответа предыдущего контейнера.

Coolify: порт 3000, health path `/api/health/ready`, start period 150 секунд,
остановка до 50 секунд, restart `unless-stopped`, постоянный том `/storage`.
Не запускать старый и новый контейнер как два постоянно работающих экземпляра.
Для обновления используется rolling deployment без фиксированного имени контейнера:
Coolify скачивает образ при работающей старой версии и проверяет новую до переключения.
На время переключения новый контроллер ожидает advisory lock в режиме standby;
HTTP готов только при свежем heartbeat работающего контроллера. После остановки
старого контейнера новый забирает блокировку и продолжает очередь. Этот переход
проверяется на GitHub двумя временными контейнерами с общей тестовой БД.
Реальный релиз `54481b452f3f672b5386eb36a526d663e33b1a1f` прошёл весь
workflow GitHub и переключение Coolify; ПК сам скачал соответствующий релиз,
сверил архив и запустил шесть медиаочередей. При передаче управления был один
503 от readiness, следующий опрос через 5 секунд прошёл. После обновления
повторно прошли 41 проверка доступа через публичный HTTPS и выдача файлов S3.
Локальный контроллер процессов завершает весь контейнер при падении процесса
или повторном провале readiness: один Docker HEALTHCHECK сам по себе не делает restart.
Очереди находятся в PostgreSQL, файлы — за пределами заменяемого контейнера.

Для первого запуска обязательны `DATABASE_URL`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`.
Для OAuth: `WEB_ORIGIN` и `API_ORIGIN` равны `https://clipforge.clanvelt.com`.
Секреты Twitch, YouTube и S3 задаются runtime-переменными Coolify, не build args.
`AUTO_PUBLISH_ENABLED=false` сохраняется до завершения проверки YouTube.

## База данных

Версионные миграции находятся в `packages/db/migrations`. Запуск ожидает БД и
применяет их под advisory lock до старта HTTP и планировщика. Новая база
создаётся автоматически; последующие запуски не сбрасывают данные.
Существующую базу без истории миграций запуск намеренно не переопределяет:
нужны резервная копия, сверка схемы и явная фиксация исходной версии.
`drizzle-kit push --force` при деплое не используется.

## Медиа

Endpoint: `https://s3.ru1.storage.beget.cloud`, регион `ru1`, бакет
`caa1f346709c-clanvelt`, отдельный префикс `clipforge/`.
Локальные секреты — `.env.s3.local`, исключены из Git и Docker context.
API проверяет доступ к конкретному клипу до выдачи подписанной ссылки на 5 минут.
Бакет закрыт: это подтверждено реальной проверкой анонимного запроса.
Воркер сначала загружает видео и превью, проверяет размер и SHA-256 объектов, затем
добавляет ссылку в каталог. Имена объектов привязаны к версии клипа.
Повторная загрузка того же содержимого пропускается после HEAD; чтение диапазона
байтов позволяет продолжить отправку в YouTube с подтверждённой позиции.
Исходники и промежуточные файлы остаются на ПК.

`node apps/worker/dist/sync-media.js` переносит только неархивные клипы,
сохраняя локальные оригиналы. `node apps/worker/test/storage.integration.mjs`
проверяет реальный S3 небольшим временным объектом и удаляет свой объект.

## Границы отказоустойчивости

Один сервер не обеспечивает доступность при отказе самого ishosting. В Coolify
настроена ежедневная копия только БД `clipforge` в Beget S3 (23:15 UTC),
три локальные копии и пять в S3. Часовой host timer `clipforge-backup-retention`
запускает `docs/ops/coolify-backup-retention.php` в Coolify: локальные копии старше
трёх дней и S3-копии старше пяти дней удаляются по текущему времени, даже если
новый бэкап не создался. Скрипт проверяет БД, UUID и полный шаблон имени файла.
Другие базы и префиксы бакета не затрагиваются. Ошибка таймера видна в systemd;
недоступное хранилище требует устранения сбоя, а не обещания гарантированной очистки.
Копия скачана обратно из закрытого S3
и восстановлена в отдельную временную БД: аккаунт, четыре актуальных клипа и
две версии миграций сохранены; временная БД после проверки удалена.
Сессия resumable upload сохраняется до передачи видео. После сбоя обработчик
запрашивает принятую позицию у YouTube и продолжает ту же сессию; завершённая
сессия возвращает исходный video ID. Просроченная сессия или прежняя загрузка
без сохранённой сессии требует проверки канала перед новой отправкой.

## Ограничения обработки на ПК

`MEDIA_NETWORK_KBPS=10000` ограничивает скачивание Twitch и отправку файлов в S3.
Одновременно выполняется одна тяжёлая задача, один download-поток и один рендер.
Готовые обновления worker также скачиваются с этим лимитом, только после
остановки предыдущего worker. Во время работы проверяется лишь наличие релиза,
чтобы скачивание обновления не складывалось с трафиком Twitch/S3.
Лимит относится к полезным данным ClipForge, а не к трафику других программ ПК.
Для исходной верхней границы 40 Мбит/с настройки выше 40000 запрещены.

Windows launcher помещает supervisor и всё дерево media-процессов в Job Object:
`MEDIA_MEMORY_MB=4096` — общий предел committed RAM, `MEDIA_CPU_PERCENT=20` —
предел CPU, приоритет Below Normal. Предел устанавливается до запуска кода.
GPU-память не входит в предел Windows RAM; её потребление сокращают
`SPEECH_BATCH_SIZE=1` и `SPEECH_COMPUTE_TYPE=int8_float16`.
`MEDIA_MIN_FREE_MB=8192` откладывает запуск при нехватке свободной RAM.
Launcher ожидает появления памяти с интервалом 30 секунд.

Распознавание идёт окнами по `SPEECH_WINDOW_SECONDS=300`, с двухсекундным
перекрытием и переводом слов в исходные таймкоды. Готовые окна сохраняются
атомарно; перезапуск продолжает с последнего окна. Спектр аудио считается
блоками, без одновременного создания полной комплексной FFT-матрицы.

Задача Windows `ClipForge Media Worker` запускается при входе в Windows и
проверяет запуск каждые пять минут. `StartWhenAvailable` включает пропущенный
запуск; второй экземпляр игнорируется. Это автозапуск после входа пользователя,
а не служба, работающая до входа. Сборки остаются только на GitHub.

## Восстановление и удаление данных YouTube

До `pg_restore` остановить приложение и обработчик на ПК. После восстановления
и применения миграций, до запуска HTTP и очередей, выполнить в текущем образе:

```sh
node scripts/sanitize-restored-database.mjs --confirm-database=clipforge
```

Используется `DATABASE_URL` восстановленной базы. Команда отказывается работать
при активном контроллере/медиаворкере, берёт их advisory locks и очищает
YouTube-токены, API-метаданные и статистику. Собственные отметки отправленных
публикаций остаются, задания для них становятся безопасными; исходные клипы
и аккаунты ClipForge сохраняются. Автоматика ставится на паузу. После запуска
нужно заново разрешить доступ YouTube и проверить данные перед возобновлением.
Обычный перезапуск эту команду не запускает и подключения не сбрасывает.

Статистика и не обновлённые метаданные хранятся в основной БД до 21 дня.
При отзыве через приложение экранные данные удаляются сразу; недоступный
endpoint Google повторяется максимум 12 часов плюс часовой интервал обработки.
Вместе с пятидневными копиями и часовым интервалом их очистки это оставляет
запас до семи дней. При внешнем отзыве проверка выполняется ежечасно, а отсутствие
возможности подтвердить доступ более 21 дня также вызывает удаление.
Все сроки предполагают работающие БД/хост и доступность хранилища; аварии
контролируются мониторингом сервисов. Тестовые дампы после проверки удаляются.

## Восстановление 30 сентября 2026

Прод остановился после временного `EAI_AGAIN` имени контейнера PostgreSQL. После
накопленных 12 перезапусков Coolify достиг лимита 10 и выполнил `docker update --restart=no`.
Работающий контейнер восстановлен, restart policy возвращена в `unless-stopped`.
Для приложения ClipForge в Coolify `max_restart_count=0`, без постоянной остановки
после суммарного числа перезапусков. Supervisor теперь даёт readiness восстановиться
в течение трёх минут; падение отдельного процесса по-прежнему перезапускает контейнер.
Readiness продолжает сообщать 503 во время недоступности БД.

Обработчик рекламы эфиров использует локальную Qwen3-VL из уже установленного Ollama.
Серверный контейнер не загружает модель; работает только media worker на ПК.
