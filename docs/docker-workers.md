# Воркеры ClipForge

На странице **Воркеры → Подключить воркер** платформа выдаёт готовую команду
`docker run`. Выполните её на устройстве с Docker. Больше ничего копировать,
настраивать или вводить на этом устройстве не нужно. Отдельный вход в реестр
образов не требуется. Контейнер сам устанавливает компоненты, регистрируется
и появляется на странице воркеров. Терминал можно закрыть сразу после запуска.

Команда действует час и подключает один контейнер. Для следующего контейнера
получите новую команду: имя, том и ключ будут другими. Перезапуск уже
созданного контейнера использует сохранённую регистрацию.

## Управление платформой

Платформа выбирает задание с учётом свободных ресурсов и текущих назначений.
Контейнер получает только данные назначенного эфира и разрешённые операции.
Клипы, обложки и исходники передаются непосредственно в S3 по подписанным
ссылкам платформы. Части по 8 МиБ проверяются по MD5, целый файл — по размеру
и сохранённому SHA-256; при восстановлении SHA-256 пересчитывается. Уже принятые
части не отправляются повторно. Сервер не держит промежуточную копию видео.
Подборки и публикация управляются сервером: готовый клип может публиковаться
по расписанию, пока остальные ещё обрабатываются.

Контейнер не получает ключи PostgreSQL, S3, очереди или YouTube. Для S3 платформа
выдаёт временную ссылку только на конкретный файл или часть назначенного эфира.
Соединение с платформой и хранилищем — исходящий HTTPS:
открывать порты, настраивать VPN или монтировать Docker socket не нужно.
Исходник восстанавливается из S3, а при отсутствии в хранилище скачивается с Twitch.
Модели устанавливаются из публичных источников.

После успешного сохранения локальные медиа автоматически удаляются. Во время
работы используется временный диск; модели и зависимости остаются в томе.
При сбое неподтверждённый оригинал сохраняется до повторного переноса. Кэш старых
заданий переносится через `heavy.archive-vod` с теми же ограничениями скорости,
правами доступа и исключением одновременных задач одного эфира. ID воркера
сохраняется в томе и используется в интерфейсе; процессы контроллера туда не входят.

## Ресурсы

Каждый контейнер выполняет одно задание за раз. При подключении выбирается тип
заданий. Ресурсы для него заданы платформой, ручных полей CPU/RAM нет:

| Тип | Задания | CPU | Память |
| --- | --- | --- | --- |
| Каталог | Поиск и метаданные эфиров | 0,25 | 256 МиБ |
| Распознавание речи | Расшифровка аудио | 2 | 6 ГиБ |
| Монтаж и анализ изображения | Монтаж, камера, реклама, исходный звук | 2 | 2 ГиБ |
| Полный конвейер | Подготовка эфира и все этапы обработки | 2 | 6 ГиБ |

Память заранее целиком не занимается. Воркер каталога не устанавливает модели,
ffmpeg и библиотеки распознавания. Задачи речи в первую очередь получает свободный
воркер распознавания; универсальный воркер берёт их, когда специалист занят или
недоступен. Поиск эфиров передаётся подключённым воркерам каталога; при их отключении
его продолжает контроллер платформы. Полные задания подготовки пока выполняются
целиком универсальным воркером; отдельные этапы можно назначать специалистам.

Контейнер учитывает свои cgroup-ограничения, оставляет не менее 10% памяти,
снижает нагрузку при конкуренции и при необходимости приостанавливает тяжёлые
процессы. Их CPU и дисковый приоритет понижен. Для каталога сеть ограничена
1 Мбит/с на получение и 0,5 Мбит/с на передачу. Для обработки скачивание ограничено 10 Мбит/с,
передача результатов — 5 Мбит/с. Первичная установка тоже ограничивает скачивание.

В Docker Desktop контроллер видит ресурсы Linux VM; её общий максимум задаётся
в настройках Docker Desktop. Доступа к процессам Windows у контейнера нет.

## Надёжность

**Не брать новые** позволяет закончить текущее задание. **Отозвать доступ**
прекращает работу подключения; незавершённое задание переназначается.
Контейнер восстанавливает связь после перезапуска платформы.
Новая версия компонентов устанавливается автоматически между заданиями.

Назначение имеет срок действия и продлевается при связи с воркером.
При потере связи контейнер останавливает обработку раньше истечения назначения.
Просроченные и отозванные подключения не могут записывать результаты.
Принятые клипы сохраняются. Два воркера не получают один эфир одновременно.
Разные эфиры подборки выполняются параллельно; деление одного эфира
на интервалы пока не включено.

## Реализация

Команда использует официальный публичный образ `node:22-bookworm-slim`.
Загрузчик получает приватный пакет обработки после регистрации и проверяет SHA-256.
Первичная установка занимает несколько минут; зависимости и модели
сохраняются в именованном томе, медиа используется только временно. Обработчик работает без root.
В пакет не входят `.env`, код API и ключи платформы.

Workflow **Platform managed workers** проверяет две реальные команды подключения:
установку, регистрацию, распределение заданий, Python-анализ звука,
обработку настоящего видео через ffmpeg и возврат видео с обложкой в каталог.
Изолированные проверки проверяют отзыв, потерю связи, повторную передачу частей
файла, границы доступа и отсутствие одновременной обработки одного эфира.

## Исходный звук

`pnpm cf original-audio <vodId> --clips id,id` ставит восстановление исходной
дорожки в очередь платформы. Видеоряд, монтаж и субтитры сохраняются; аудио
берётся с соответствующих временных отметок исходного эфира без DTLN,
подавления пауз, изменения громкости и заглушения слов. Создаются отдельные
черновики, существующие публикации не изменяются. Полученный jobId можно передать
в `pace-batch`: публикация идёт постепенно через обычную очередь и ограничения YouTube.

Старый процесс совместим на период перехода. Его файлы доступа новым контейнерам
не нужны: они используют только регистрацию на платформе.

## Хранение медиа

Принятый клип и обложка хранятся в S3. Локальная копия удаляется сразу после
проверенной загрузки и записи в каталог, без ожидания всей подборки. Отклонённые
рендеры и промежуточные файлы не архивируются. Рабочие исходники сохраняются
в S3 только пока нужны заданиям; после завершения или отмены они очищаются.
Причины отклонения остаются в базе без ненужных видео.

Временный диск контейнера нужен во время обработки. Проверенные контрольные
точки выгружаются и локальный кэш очищается также при ошибке задания. После
аварийного выключения очистка получает приоритет при следующем запуске.
На сервере каждые 10 минут удаляются невостребованные объекты; незавершённые
загрузки, активные задания и актуальные/опубликованные клипы защищены.

Проверка старого локального каталога: `pnpm cf storage-cleanup --root <проект>`.
Добавление `--apply` выполняет план. Команда получает решение и проверенные
SHA-256 от платформы, не требует доступа к БД или ключей S3. Отдельная команда
`pnpm cf storage-gc` показывает объём ненужных объектов S3, `--apply` удаляет их.
Команды используют обычные настройки входа CLI. Единственная локальная копия
принятого клипа сохраняется до успешной загрузки в S3; активные эфиры пропускаются.

## Статистика и квота

`/analytics` — история счётчиков и фильтры; `/shorts` — опубликованные ролики;
`/publications` — очередь публикации и время следующей загрузки.
Управление содержит настройки подключений.

Google Cloud для чтения квоты настраивается только на сервере.
Без доступа остаток показывается как неизвестный. Дополнительный дневной лимит
YouTube-канала API числом не сообщает. Материалы аудита 24 сентября оставляли
производные оценки отключёнными; автоматические коэффициенты по этим оценкам
включаются только после отдельного одобрения Analytics & Reporting.
