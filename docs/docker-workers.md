# Docker-воркеры ClipForge

Один контейнер — один воркер. Он подключается к общей PostgreSQL-очереди и S3,
сам регистрируется в разделе **Воркеры** и сообщает состояние каждые 10 секунд.
Результаты доступны остальным устройствам через S3; локальные исходники и модели
остаются в отдельном томе контейнера.

## Первый запуск

Образ `ghcr.io/o-codify/clipforge-worker:fleet-preview` собирается и проверяется
workflow **Worker fleet preview**. Он не выкладывает сервер ClipForge.
Образ приватный, как репозиторий: на новом устройстве сначала нужен `docker login ghcr.io`
с правом чтения пакета. Для воспроизводимого запуска вместо `fleet-preview` можно
указать SHA проверенного коммита из workflow.

1. Установите Docker с Linux-контейнерами (amd64).
2. Скопируйте `deploy/worker.env.example` в `worker.env` и заполните доступы
   той же платформы: PostgreSQL, S3, ключи приложения. Это приватный файл;
   в Git и образ он не попадает. PostgreSQL должен быть доступен по VPN/приватной
   сети или защищённому туннелю. `localhost` внутри контейнера — сам контейнер,
   а не удалённый сервер. В Docker Desktop для сервиса на хосте используется
   `host.docker.internal`.
3. Запустите из каталога с `worker.env`:

```sh
docker run -d --name clipforge-worker --restart unless-stopped --init --cpus=4 --cpu-shares=256 --memory=8g --memory-swap=8g --pids-limit=256 --env-file worker.env --mount source=clipforge-worker-1,target=/storage ghcr.io/o-codify/clipforge-worker:fleet-preview
```

Терминал после команды можно закрыть. Для второго контейнера измените `--name`
и имя тома. Не задавайте одинаковый `WORKER_ID` двум контейнерам; по умолчанию
используется уникальный hostname. `WORKER_NAME` — только видимая подпись.

S3 обязателен в режиме нескольких устройств. Без него воркер откажется брать
задачи, поскольку сохранённые на одном компьютере клипы были бы недоступны другим.
Для публикации нужны ключи **того же** YouTube OAuth-приложения; пользовательский
refresh token уже хранится в базе подключённого канала.

Вариант с Compose: положите `worker.env` рядом с `deploy/workers.compose.yml`, затем:

```sh
docker compose -f deploy/workers.compose.yml up -d --scale worker=2
```

У каждой реплики отдельный том. Не удаляйте тома при обычном перезапуске:
там кэш исходников и модели. После пересоздания контейнер получает новый hostname;
его прежняя запись остаётся в истории как отключённый воркер.

## Ресурсы

- `--cpus` и `--memory` задают максимум **одному** контейнеру. Процесс читает
  cgroup v1/v2, а не принимает всю память хоста за свой лимит.
- Внутри лимита сохраняется запас около 10%; CPU ограничивается дополнительно
  контроллером нагрузки. При конкуренции используется низкий приоритет CPU/I/O.
- При недостатке памяти тяжёлые дочерние процессы приостанавливаются, а при
  длительном давлении освобождают память и повторяют этап с сохранённых данных.
  Связь с очередью остаётся активной.
- Новые тяжёлые задания не принимаются, если свободного места меньше
  `MIN_FREE_GB` (по умолчанию 20 ГБ).
- Скачивание по умолчанию ограничено 10 Мбит/с, загрузка — 5 Мбит/с. Это предел
  на воркер; при нескольких контейнерах сумма растёт. Делите общий бюджет сети
  между ними через `MEDIA_DOWNLOAD_KBPS` и `MEDIA_UPLOAD_KBPS`.
- Docker Desktop видит ресурсы своей Linux-VM. Он не видит нагрузку всех Windows
  приложений. Оставьте запас Windows в настройках ресурсов Docker Desktop;
  для полной адаптации к Windows остаётся существующий нативный контроллер.
- Образ работает на CPU. GPU/CUDA и ARM не заявлены как проверенные варианты.
  Минимум контейнера — 2 ГиБ, для `large-v3` используйте 8 ГиБ или больше.

DTLN и детектор камеры входят в образ. Модель речи при первом обращении
скачивается в том с ограничением скорости; повтор продолжает ту же версию файла.
Модель можно заранее положить в том и указать путь в `SPEECH_MODEL`.

## Распределение и восстановление

Воркер захватывает тяжёлую задачу только после освобождения своего слота.
Два лёгких слота продолжают публикации и короткие операции параллельно.
Подборка нескольких эфиров раскладывается на дочерние задания по эфирам;
координатор не занимает тяжёлый слот. Один эфир защищён блокировкой PostgreSQL,
поэтому две машины не скачивают и не режут его одновременно. Деление одного
эфира на параллельные интервалы пока не реализовано.

Кнопка **Не брать новые** завершает текущую работу и исключает воркер из новых
назначений. **Принимать задания** возвращает его в работу. На странице заданий
можно выбрать воркер, состояние или открыть повторяющиеся задачи.

При потере воркера недостаточно одного устаревшего heartbeat: восстановление
проверяет освобождение его сессионной блокировки PostgreSQL. Только затем его
задания повторяются. Готовые результаты и идентификатор подборки сохраняются.
Неопределённый исход загрузки YouTube автоматически заново не отправляется.

Для перехода со старой версии сначала установите совместимую версию платформы,
затем остановите старый media-процесс и запускайте контейнеры. Старый бинарник
держит исключительную блокировку: новые контейнеры не начнут работу поверх него.
Эта доработка сама по себе не переключает и не останавливает рабочий ПК.

## Статистика и квота

`/analytics` — история счётчиков, фильтры и сводка всей выборки;
`/shorts` — каталог опубликованных роликов;
`/publications` — очередь, прогресс передачи и время следующей загрузки.
Управление содержит только настройки подключений.

Точный расход квоты проекта читается из Google Cloud. На сервере API и
контроллере задайте `GOOGLE_CLOUD_PROJECT` и путь `GOOGLE_APPLICATION_CREDENTIALS`
к read-only учётным данным с доступом Service Usage Viewer и Monitoring Viewer.
При контейнерном запуске файл монтируется read-only. Если доступ не настроен,
интерфейс показывает неизвестный остаток, а не выдуманный лимит 100.
Дополнительный дневной лимит самого YouTube-канала API числом не сообщает.
Его отказ останавливает новые попытки на 24 часа; квота проекта — до полуночи
Pacific. Между проверками учитываются новые локальные попытки videos.insert.

Материалы аудита 24 сентября заявляли базовые счётчики и прямо оставляли
производные оценки отключёнными. Поэтому расчёт коэффициентов отбора реализован,
но включается только после отдельного одобрения Analytics & Reporting.
История API-данных и производные записи очищаются по существующему сроку 21 день.
