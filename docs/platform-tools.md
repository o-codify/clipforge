# Управление ClipForge через API

Штатный клиент платформы: `pnpm cf --help`. Исходники находятся в `apps/cli`.
Это HTTP-клиент того же API, которым пользуется сайт: он не подключается к БД,
не читает серверный `.env`, не выполняет SSH и не получает OAuth-токены YouTube.
Команды возвращают JSON; тяжёлую работу выполняет обычный worker.

## Подключение

Задать `CLIPFORGE_URL` явно: например `http://127.0.0.1:8420` для локального API
или HTTPS-адрес установленной платформы. Автоматического переключения между
локальной и действующей версией нет.

Передать `CLIPFORGE_LOGIN` и `CLIPFORGE_PASSWORD` через окружение процесса,
а не аргументы командной строки или отслеживаемые файлы. Клиент входит через
`/api/auth/login`, выполняет команду и закрывает временную сессию через logout.
Можно передать `CLIPFORGE_SESSION` вместе с её `CLIPFORGE_URL`: такую сессию
клиент не закрывает. Самостоятельно извлекать сессии из профиля браузера не нужно.
Для административных операций нужны права администратора; режим просмотра
от имени пользователя сохраняет свои ограничения.

## Публикация

Для одного экспериментального клипа из другого момента эфира:
`pnpm cf render <vodId> --count 1 --fresh --audio dtln`.
`--fresh` исключает пересечение с клипами в каталоге и публикациями этого эфира;
`--audio dtln` обрабатывает звук только этого задания, без заглушения пауз речи.
Без этого параметра сохраняется оригинальная дорожка. Требуются актуальные API
и media-worker: для этих параметров используется отдельная очередь
`heavy.render-variant`, которую старые версии не заберут. После задания
проверьте `protection.audio.method = dtln` и просмотрите результат перед публикацией.

1. `pnpm cf clips --streamer sany_jeweler` — выбрать существующий клип.
2. `pnpm cf clip <clipId>` — посмотреть состояние, версию и результаты проверки рекламы.
3. Если нужна обработка: `pnpm cf cleanup <clipId>`, затем `pnpm cf wait <jobId>`.
   Команда создаёт задание скрытия QR-кодов и рекламы, не меняет аудио.
   Для ручных областей есть `--regions regions.json` (массив `{x,y,w,h}`).
4. После реального просмотра результата: `pnpm cf approve-clip <clipId>`.
   Это явное подтверждение проверки, его нельзя выполнять автоматически вместо просмотра.
5. `pnpm cf preview <clipId>` — получить название, описание с хештегами и доступные каналы.
6. Сохранить выбранные параметры в JSON и выполнить
   `pnpm cf publish <clipId> --metadata publication.json`.

```json
{
  "accountId": "идентификатор-подключения",
  "title": "Sany_Jeweler | Dota 2 #Dota2 #sany_jeweler",
  "description": "Sany_Jeweler\nhttps://www.twitch.tv/sany_jeweler\n\n#Dota2 #дота #sany_jeweler",
  "privacy": "public"
}
```

Ответ содержит `publicationId`, `jobId`, `queued`, `existing`. Повтор команды
не создаёт вторую публикацию. Потерянная постановка со статусом queued может
быть восстановлена тем же запросом. Неизвестный исход уже начавшейся загрузки
по-прежнему блокирует повтор, чтобы не получить дубликат на YouTube.

`pnpm cf wait <jobId>` ждёт с интервалом 5–15 секунд; код выхода 0 — завершено,
1 — ошибка/отмена, 2 — время ожидания истекло, задание продолжает работать.
Клиент не повторяет HTTP-мутации автоматически при сетевой ошибке.

Публикация — внешнее действие, её нужно выполнять только в пределах поручения
пользователя. Проверка видео не является разрешением загружать ещё одно.
Повторную загрузку старого приватного видео эта команда намеренно не делает:
отдельной операции повторной публикации пока нет. Нельзя обходить это ограничение
клонированием клипов в БД или вызовом worker-функций из временных скриптов.

## Проверка и статистика

- `pnpm cf publication <publicationId>` — сохранённые факты и время проверки.
- `pnpm cf refresh <publicationId>` — поставить проверку одного видео в очередь.
- `pnpm cf refresh` — обновить все подключённые каналы.
- `pnpm cf analytics --page 1` — прочитать последние счётчики.
- `pnpm cf jobs`, `pnpm cf job <jobId>` — обычная история заданий платформы.
- `pnpm cf youtube-check <accountId>` — проверить доступ к каналу, без загрузки.

В интерфейсе «Управление → Публикации» кнопка «Обновить из YouTube» использует
тот же API и очередь. После окончания задания таблица перечитывает результаты.
Ежечасный сбор и проверка после загрузки используют тот же сборщик. Одновременные
сборы защищены общим замком; повторные задания объединяются в очереди.

Новые маршруты администратора:

| Запрос | Результат |
| --- | --- |
| `GET /api/platforms/publications/:id` | Сохранённая публикация, последнее измерение, задание |
| `POST /api/platforms/youtube/refresh` с `{}` или `{publicationId}` | `{jobId, queued}` |
| `GET /api/jobs/:id/status` | Ход выполнения и результат задания |

`actualPrivacy` берётся из ответа YouTube, а не желаемой настройки при отправке.
`stale` и `collectedAt` показывают актуальность данных; отсутствующие счётчики —
`null`, а не ноль. `restrictions` содержит региональные и возрастные ограничения.
`copyrightClaim: "unknown"` означает, что стандартный API не сообщает детали
Content ID: отсутствие регионального ограничения не подтверждает отсутствие
музыкальной претензии. Эти детали проверяются в Studio.

По умолчанию обработка сохраняет звук эфира, фоновую музыку не добавляем.
DTLN включается в карточке стримера для всех его текущих и будущих эфиров или
в карточке отдельного эфира. Настройка эфира имеет приоритет; «Как у стримера»
снимает переопределение. Выбор действует только на новые клипы, включая
автоматическую нарезку. Исходные записи и готовые клипы не изменяются.
DTLN работает без заглушения пауз речи и может ослаблять звуки игры.
Ни фильтрация, ни скрытие рекламы не гарантируют отсутствие музыкальных претензий.

```powershell
pnpm cf streamer-audio sany_jeweler --audio dtln
pnpm cf vod-audio v2859643784 --audio dtln
pnpm cf vod-audio v2859643784 --audio inherit
pnpm cf render v2859643784 --test-batch --count 10
```

API: `POST /api/streamers/:login/audio` с `{audioMode:"original"|"dtln"}` и
`POST /api/vods/:id/audio` с `{audioMode:null|"original"|"dtln"}`. Только администратор.
`GET /api/vods/:id` возвращает `audio.mode`, `audio.override`, `audio.streamerMode`,
`audio.source`. Настройка считывается один раз при начале нарезки и сохраняется
в параметрах прогона, чтобы изменение настройки не смешивало режимы внутри него.
Явный `render --audio` переопределяет её только для одного задания.

`--test-batch` — явная административная подборка до 20 новых черновиков,
в том числе в режиме разработки. Моменты не пересекаются с существующими
видимыми/опубликованными клипами и между собой. Обычные задания в режиме
разработки по-прежнему создают один клип. Подборка ничего не публикует.
При повторе прерванного задания подборка продолжает тот же прогон и учитывает
уже сохранённые клипы в общем количестве. Результат обработки сохраняется
для каждого клипа отдельно, а выбранный режим звука остаётся прежним.
`--fresh`, `--audio` и `--test-batch` используют очередь `heavy.render-variant`,
которую старые версии воркера не получают. Отсутствие результата DTLN — ошибка,
а не разрешение незаметно вернуть исходный звук.

Если исходник ещё не подготовлен, используйте
`pnpm cf prepare <vodId> --count 6 --audio dtln`.
Это административная очередь `heavy.prepare-preview`: загрузка, распознавание,
анализ, поиск камеры и нарезка до 20 новых черновиков. Параметры звука относятся
только к этой подборке. Публикации не создаются; `testBatch` и `skipExisting`
всегда включены, старый worker эту очередь не получает. Готовые этапы повторно
не выполняются, а сохранённые исходники можно использовать и после удаления
эфира с Twitch. Несколько эфиров готовятся последовательно в общей media-очереди.

## Локальный media-worker

`scripts/media-pc.mjs <runtime-home> --workspace <путь-к-репозиторию>` запускает
скомпилированный worker из рабочей копии через обычный туннель и блокировку роли.
В этом режиме он не устанавливает релиз и не запускает автообновление.
На Windows supervisor нужно запускать через `scripts/run-media-limited.py`
с адаптивным контролем ресурсов. Перед запуском остановите установленное
задание планировщика и его дерево процессов; после проверки восстановите его.
`WORKER_QUEUES=heavy.render-variant` ограничивает временный worker только выбранной нарезкой,
отключает планирование и очистку исходников. Не запускайте два media-worker одновременно.

## Проверки разработки

`pnpm exec tsc -b apps/cli apps/api apps/worker`

`node --test apps/cli/test/*.test.js`

`node apps/api/test/platform-tools.isolated.mjs`

Интеграционная проверка поднимает настоящий HTTP API с обычной авторизацией
и очередью на одноразовой локальной БД. Ответы Google подменены; видео не загружаются.
Она не использует DATABASE_URL из `.env`, поскольку там может быть туннель к серверу.

Новые маршруты требуют обновления API и control-worker вместе. Локальные изменения
не означают, что они уже установлены на действующем сайте.

## Постепенная публикация подборки

`pnpm cf pace-batch <jobId> --channel UC… --interval 10 --daily-limit 100`
разрешает публичную отправку только клипов этой подборки, включая новые результаты
по мере рендера. `pnpm cf batch-publications` показывает состояние,
`pnpm cf pause-batch <jobId>` останавливает новые отправки (текущая загрузка может завершиться).
В интерфейсе управление находится на странице стримера и в настройках публикаций.

API: `POST /api/platforms/batches/:jobId`, `GET /api/platforms/batches`,
`DELETE /api/platforms/batches/:jobId`. Все маршруты доступны только администратору.
Настройки хранятся в `platform_runtime`, ключ `batch-publication:<jobId>`.
По умолчанию подготовка подборки остаётся только созданием черновиков.

Media-worker раз в 30 секунд подхватывает один готовый клип и создаёт отдельное
задание `light.publish-batch-clip`. Эта очередь работает параллельно тяжёлой нарезке;
старый control-worker её не обслуживает. Нужны обновлённые локальные API и media-worker.
Браузер не обязан оставаться открытым, но локальный media-worker должен работать.

Следующая отправка — не раньше заданного интервала после завершения предыдущей.
Лимит — консервативное скользящее окно 24 часа по попыткам публикации канала,
включая ручные отправки; это внутреннее ограничение, а не утверждение о квоте Google.
После простоя очередь не отправляет накопленные ролики разом. Отсутствие подключения
даёт состояние `waiting-channel`; подключение того же канала возобновляет очередь.
Неизвестный исход загрузки и ошибки публикации останавливают эту подборку для проверки,
а не запускают слепую повторную отправку.

`pnpm cf resume-batch <jobId>` (`POST /api/jobs/resume-batch/:id`, администратор)
продолжает завершившуюся с ошибкой нарезку с тем же идентификатором и сохранёнными
клипами. Политика постепенной публикации сохраняется. Команда не повторяет загрузки
YouTube, не возобновляет отменённые подборки и не создаёт вторую активную подборку.

В адаптивном режиме (`MEDIA_MEMORY_MB=0`) память регулируется ожиданием перед
тяжёлыми этапами, приостановкой и освобождением Python/FFmpeg при нехватке ресурсов.
Жёсткий лимит committed memory не уменьшается на ходу: это приводит к ошибкам
выделения памяти вместо паузы. Явный `MEDIA_MEMORY_MB` задаёт постоянный аварийный
предел. Приоритет процессов и адаптивный предел CPU до 90% действуют в обоих режимах.

Отдельная запись outbox хранится до постановки pg-boss, поэтому перезапуск между
созданием публикации и постановкой задания не теряет клип и не создаёт дубль.
Запрещённые/архивные клипы и клипы без подтверждения обработки рекламы (либо
сохранённого отключения этой проверки) не выбираются.
