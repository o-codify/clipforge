> Актуальный запуск и устройство платформы: README.md и docs/platform-status.md. Старое Python-приложение находится в legacy; основная платформа — apps/web, apps/api, apps/worker. Из Python используются вычислительные workers/python. Автоматика запускает нарезку без одобрения каждого эфира. Помощник — отдельный packages/assistant. Ниже сохранены исходные заметки; описания ручного запуска могут быть устаревшими.

# Архитектура

Площадка, которая сама находит стримеров, режет их эфиры на вертикальные
клипы и публикует их. TypeScript-проект, внутри которого живут
python-воркеры — не наоборот.

```
┌─ apps/web ──────────┐   Next.js: интерфейс админа и стримера
│                     │
├─ apps/api ──────────┤   NestJS: владеет схемой, очередью, расписанием,
│                     │   правами. Единственный, кто ходит в базу.
├─ apps/worker ───────┤   Node: берёт задания из очереди, гоняет yt-dlp,
│                     │   ffmpeg и python-воркер
├─ packages/db ───────┤   Drizzle: схема и миграции
├─ packages/contracts ┤   zod-схемы обмена, общие для всех
├─ packages/pipeline ─┤   нарезка на TS: детекция, субтитры, ffmpeg
│                     │
└─ workers/python ────┘   ровно три анализатора
```

## Почему Python остался, и ровно столько

Python держится в проекте только там, где он действительно сильнее:

| Задача | Почему Python |
|---|---|
| распознавание речи | faster-whisper на CUDA, аналога в Node нет |
| сигналы звука | numpy: БПФ, скользящие окна, автокорреляция |
| поиск вебки | OpenCV YuNet; биндинги для Node заброшены |

Всё остальное переехало или переедет в TypeScript, потому что там Python
не давал ничего:

- **yt-dlp** — отдельный бинарник, его запускает кто угодно;
- **ffmpeg-рендер** — сборка строки фильтрграфа;
- **субтитры ASS** — генерация текста по таймкодам слов;
- **детекция кандидатов и отбор** — арифметика по массивам, которые
  вернул анализатор;
- **мат, реестр, интерфейс** — обычный прикладной код.

Правило: если задача одинаково делается в обоих языках, она делается в
TypeScript. Тогда доменная логика лежит в одном месте — там же, где
права, настройки и очередь.

## Воркер не знает о площадке

Python-воркер получает пути к файлам и возвращает числа. Он не ходит в
базу, не знает про стримеров, игры и прогоны, не имеет очереди и
расписания. Единственное состояние между заданиями — кэш загруженных
моделей.

Это не эстетика. Пока воркер знал раскладку проекта, он вычислял путь к
модели детектора от собственного расположения — и сломался ровно в тот
момент, когда файл переехал. Теперь путь передаёт бэкенд, и переезжать
можно свободно.

### Протокол

Долгоживущий процесс, NDJSON по stdin/stdout: строка на сообщение.

```
-> {"id":"7","op":"audioSignals","params":{"audio":"…","out":"…"}}
<- {"event":"progress","id":"7","stage":"спектр и сигналы","value":null}
<- {"event":"log","id":"7","level":"info","message":"кадров 81893"}
<- {"id":"7","ok":true,"result":{…}}
```

Процесс долгоживущий, потому что модель `large-v3` поднимается около
двадцати секунд и занимает пару гигабайт видеопамяти. Запуск на каждое
задание означал бы платить это каждый раз.

Задания идут строго по одному: воркер упирается в видеокарту, и
параллельные запросы поделили бы память и замедлили оба.

**Числовые массивы через трубу не гоняются.** Часовой эфир — это 81 893
кадра на девять рядов; в JSON это десятки мегабайт на разбор. Воркер
пишет их одним бинарником float32 LE, ряд за рядом, и возвращает путь,
число кадров и порядок рядов. TypeScript читает его как `Float32Array`
без копирования:

```ts
const all = new Float32Array(buf.buffer, buf.byteOffset, buf.byteLength / 4);
const combat = all.subarray(8 * frames, 9 * frames);
```

Порядок рядов задан в двух местах — `packages/contracts/src/worker.ts` и
`workers/python/clipforge_worker/__main__.py`. Файл не самоописателен,
поэтому менять их можно только вместе.

## Postgres, а не SQLite

SQLite упирался в то, что соединение привязано к потоку, а веб-обработчики
живут в пуле: приходилось открывать базу на каждый запрос. С несколькими
стримерами, планировщиком и воркерами это перестаёт работать вовсе.

Очередь заданий тоже в Postgres (pg-boss). Отдельный Redis на одной
машине — это лишний демон и лишний источник отказов.

## Как проверяется перенос

В конвейере накоплено поведение, найденное опытным путём, и переписать
его «примерно так же» нельзя. Поэтому каждый перенесённый кусок
сверяется с python-реализацией на одних и тех же входных данных:
эталоны сняты со старого кода и лежат в
`packages/pipeline/test/fixtures`.

```bash
pnpm --filter @clipforge/pipeline test
```

Сверяется не «похоже», а точное совпадение: граф фильтров сравнивается
строкой, потому что любая перестановка звеньев меняет картинку.

Первый же прогон поймал настоящий регресс: в JavaScript граница слова
`\b` работает только по латинице, поэтому «манда» начала ловиться в
«мандарине», а «суки» — в «сукине». В Python эти шаблоны защищены
замыкающим `\b`; в TypeScript пришлось выразить границу явно. Второй
регресс нашёлся в сглаживании: `np.convolve(mode="same")` при чётном
окне охватывает на отсчёт больше назад, чем вперёд, а окно там ровно
40 отсчётов — перепутанные стороны сдвинули бы весь сигнал на кадр.

### Сверка готового клипа

Финальная проверка — один и тот же момент, отрендеренный обеими
реализациями:

| Что | Результат |
|---|---|
| разрешение, длительность, кадры | совпадают: 1080x1920, 31.47 с, 944 кадра |
| размер файла | 14 848 853 против 14 848 908 байт |
| PSNR по видео | 56 дБ в среднем, минимум 40 дБ по кадрам |
| аудиодорожка | побайтово идентична |

Единственный источник расхождения — центровка имени канала в шапке. Она
считается по ширине текста, которую раньше мерил PIL, округляя каждый
глиф отдельно; fontkit складывает ширины в единицах шрифта и округляет
один раз. Разница до трёх пикселей на строку, при центровке — сдвиг на
один пиксель. Он и даёт 56 дБ вместо бесконечности.

Старый python-проект (`clipforge/`) на время переноса остаётся рабочим и
служит эталоном для сверки. Удаляется, когда TS-конвейер даёт тот же
результат.


## Очередь и порядок шагов

Задания разложены по очередям `light.*` и `heavy.*`, но **префикс сам по
себе ничего не гарантирует**: это разные очереди, и pg-boss обслуживает
каждую своим циклом. Первая версия ставила пять шагов конвейера пятью
заданиями и полагалась на «очередь одна, значит по порядку» - все пять
стартовали одновременно, и рендер упал через ноль секунд, не дождавшись
сигналов.

Порядок обеспечивают две разные вещи, и обе нужны:

- **очередь `heavy.pipeline`** - одно задание, внутри которого шаги
  вызываются подряд. Зависимость между шагами выражена явно, а не
  надеждой на расписание;
- **общий замок в процессе воркера** - одно тяжёлое задание за раз,
  независимо от того, из какой очереди оно пришло. Иначе рендер и
  распознавание делят видеопамять.

Каждый шаг идемпотентен и хранит результат в базе, поэтому повторный
прогон пропускает готовое:

```
шаг 2/5: распознавание речи → расшифровка уже есть
шаг 5/5: нарезка → [1/4] уже есть, версия 1-860024
✔ heavy.pipeline за 0.3 с {"rendered":0,"skipped":4}
```

Против 114 секунд у первого прогона.

## Что где хранится

| Данные | Где | Почему |
|---|---|---|
| стримеры, игры, эфиры, прогоны, клипы | Postgres | ими владеет бэкенд |
| расшифровка речи | Postgres, jsonb | по ней ищут и строят субтитры |
| результат поиска камеры | Postgres, jsonb | это решение конвейера |
| сигналы звука | файл `signals.f32` | 80 тысяч кадров на 9 рядов |
| аудио, видео, клипы | файлы | гигабайты |

Рядом с видео больше не валяются `info.json`, `transcript.json` и
`facecam.json`: правда о состоянии эфира была размазана между файлами и
базой, и они расходились.


## Права и область видимости

Защита включена **для всего сразу**: маршрут открыт, только если помечен
`@Public()`. Обратный порядок - закрывать по списку - рано или поздно
оставляет незакрытый маршрут, и узнают об этом не разработчики.

Область видимости решается в одном месте - в каталоге. Стример видит
только свой канал, и это выражено единственной функцией `only()`, а не
проверкой в каждом обработчике: забытая проверка в одном маршруте
означала бы, что чужой канал видно целиком.

**Просмотр от лица стримера.** Админ может смотреть площадку его
глазами: подменяется только видимость, аккаунт остаётся своим. Поэтому в
журнале действий виден настоящий автор, а не тот, за кого смотрели.

Регистрация выключена намеренно. Пока площадкой пользуется один человек,
открытая форма регистрации - это только дыра. Аккаунты стримеров заводит
администратор.

Пароли - scrypt из стандартной библиотеки: он специально медленный и
требовательный к памяти, поэтому перебор по украденной базе стоит дорого.
Проверка идёт даже когда аккаунта нет: иначе по времени ответа видно,
какие логины существуют.

Пароля по умолчанию не существует. Если `ADMIN_PASSWORD` не задан, он
генерируется при первом запуске и печатается в журнал один раз:
«admin/admin» на машине, смотрящей в сеть, живёт до первого сканера.

## Как запустить

```bash
pnpm db:up        # Postgres в контейнере
pnpm build        # сборка всех пакетов
pnpm api          # бэкенд на :8420
pnpm worker       # воркер: очередь, ffmpeg, python
```


## Интерфейс

Next.js, боковое меню в духе YouTube: сверху разделы, ниже два
раскрывающихся списка - стримеры и игры. Раскрытие запоминается:
переключаться между каналом и игрой приходится постоянно, и
схлопывающийся при каждом переходе список злит быстрее всего. Рядом с
именем видно, кто сейчас в эфире.

Запросы к бэкенду идут через собственный адрес фронта - Next проксирует
`/api` и `/media`. Иначе браузер обращался бы на другой порт, а значит
понадобились бы CORS и cookie между источниками. Проксирование убирает
оба вопроса разом, и в бою ничего менять не нужно.

Список игр строится по `streamer_games`, а не по скачанному. Иначе в
меню видна ровно одна игра - та, до которой дошли руки, - хотя стример
играет в пять.

Эфир виден в каталоге сразу, со статусом: «в каталоге», «качается»,
«готов». Раньше строка появлялась только после первого прогона, и список
архивов предлагал добавить то, что уже добавлено.
